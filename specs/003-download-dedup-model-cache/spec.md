# 功能規格:加入下載的重複判定與模型目錄快取

**功能分支**:`003-download-dedup-model-cache`

**建立日期**:2026-11-13

**狀態**:草稿

**輸入**:使用者描述:「迭代 003,建立在 002 之上。範圍只有兩件:Q21:加入下載時,沒寫版本的名稱(`qwen2.5`)要和已下載或已在佇列的 `qwen2.5:latest` 判定為同一個,不能重複加入(現在會重複加入,佇列重複時回 500)。Q179:`GET /api/models` 每次都跑一次 `colab exec`(實測 2.4–12.9 秒),改成每個工作階段快取一次。Q22(G-02 超時)不在這次範圍。」

## 使用者情境與測試 *(必填)*

### 使用者故事 1 - 沒寫版本的名稱不會被重複加入下載(優先順序:P1)

使用者在「下載模型」頁直接輸入 `qwen2.5`(沒寫版本)按「加入下載」,而執行環境上已經有 `qwen2.5:latest`,或佇列裡已經排著 `qwen2.5:latest`。系統要把兩者認成同一個模型,在試算時就告訴使用者「已下載」或「已在佇列」,不再多排一筆,也不回 500。

**為何是這個優先順序**:001 的合約寫「沒寫版本視為 `latest`」,002 已經讓取大小時補上 `latest`,但重複檢查還用原樣的名稱比對(002 plan.md Q21);結果是同一個模型被排兩次、白白重下載,或撞到佇列的唯一限制回 500。這是使用者真的會按到的地方,只做完這個故事就能消掉這個錯。

**獨立測試**:工作階段就緒(替身),執行環境上有 `qwen2.5:latest`、佇列裡排著 `llama3.2:latest` → 分別以 `qwen2.5`、`llama3.2`、`["qwen2.5:7b","qwen2.5:7b"]` 呼叫 UI API 的試算與加入下載 → 確認前兩次回 409 與對應的 `code`、佇列不變;第三次只加入一筆;沒有任何一次是 500。

**驗收情境**:

1. **假如**執行環境上已有 `qwen2.5:latest`,**當**使用者輸入 `qwen2.5` 按「加入下載」試算,**則**UI API 回 409、`code` 為 `MODEL_ALREADY_DOWNLOADED`、`model` 為 `qwen2.5:latest`。
2. **假如**執行環境上已有 `qwen2.5:latest`,**當**使用者輸入 `qwen2.5` 並確認加入下載,**則**UI API 回 409、`code` 為 `MODEL_ALREADY_DOWNLOADED`,佇列不變。
3. **假如**佇列裡有排隊中或下載中的 `qwen2.5:latest`,**當**使用者以 `qwen2.5` 試算或確認加入下載,**則**UI API 回 409、`code` 為 `DOWNLOAD_ALREADY_QUEUED`、`model` 為 `qwen2.5:latest`,佇列不變,不回 500。
4. **假如**執行環境上已有 `qwen2.5:latest`,**當**使用者以 `qwen2.5:7b` 加入下載,**則**照常加入佇列(不同版本不算重複)。
5. **假如**同一批同時勾了 `qwen2.5` 與 `qwen2.5:latest`(兩者都還沒下載、也不在佇列),**當**使用者試算並確認加入下載,**則**試算的總大小只算一次,佇列只多一筆 `qwen2.5:latest`。
6. **假如**勾選了三個模型,第二個是 `qwen2.5` 而佇列裡已有 `qwen2.5:latest`,**當**確認加入下載,**則**UI API 回 409、`code` 為 `DOWNLOAD_ALREADY_QUEUED`,三個都沒有加入佇列。
7. **假如**佇列裡的 `qwen2.5:latest` 已經是下載失敗,**當**使用者以 `qwen2.5` 加入下載,**則**照常加入一筆新的(失敗的那筆不算在佇列中)。

**功能需求**:

- **FR-001**:試算與加入下載判斷一個模型是否「已下載」或「已在佇列」(排隊中、下載中)之前,系統必須先把沒寫版本的名稱補成 `<名稱>:latest`,再和執行環境上已下載的模型名稱與佇列中的名稱比對;相同時照 001 `ui.openapi.yaml` 的 `estimateDownloads`、`enqueueDownloads` 回 409 `MODEL_ALREADY_DOWNLOADED` 或 `DOWNLOAD_ALREADY_QUEUED`,`model` 為補過版本的名稱,整批不加入佇列。
- **FR-002**:同一批裡補過版本後相同的名稱,系統必須視為同一個模型:試算只算一次大小,加入下載只加入一筆。

**非功能需求**:

- **NFR-001**:判定為「已下載」或「已在佇列」時,系統必須在向 registry 取任何 manifest 之前回應,不為重複的模型多送請求。

### 使用者故事 2 - 模型目錄打開不用每次等 `colab exec`(優先順序:P2)

使用者在「模型」頁看執行環境上已下載的模型。目錄要標出「可能無法載入」(模型大於顯示記憶體總量),這個總量要經 `colab exec` 到執行環境上讀,001 實測每次 2.4–12.9 秒、有一次超過 30 秒。同一個工作階段的顯示記憶體總量不會變,所以只讀一次,之後打開目錄、推送 `models.updated`(現在只有預先載入結束時推送)、預先載入都沿用,不再等。

**為何是這個優先順序**:這是效能問題,不會算錯或白扣 compute units;但模型頁每次打開都要等好幾秒,有時逾時,天天會碰到。排在故事 1 之後,因為故事 1 會讓佇列出錯。

**獨立測試**:工作階段就緒(替身),讓讀顯示記憶體的替身每次延遲 3 秒並計數 → 連續呼叫 `GET /api/models` 10 次 → 確認 `colab exec` 只跑 1 次、第 2 次起每次在 1 秒內回應、`vramBytes` 每次相同 → 換一個工作階段再呼叫一次 → 確認重新讀了 1 次。

**驗收情境**:

1. **假如**工作階段剛就緒,**當**使用者第一次打開模型目錄,**則**系統經 `colab exec` 讀一次顯示記憶體總量,`vramBytes` 為讀到的值。
2. **假如**這個工作階段已經讀過顯示記憶體總量,**當**使用者再次打開模型目錄,或按「預先載入」(載入結束時推送 `models.updated`),**則**系統不再跑 `colab exec`,`vramBytes` 與第一次相同。下載完成時不推送 `models.updated` 是 001 的已知缺口(001 完成報告 Q188、Q192),這一輪不補,所以沒有「下載完成後的推送」可以驗;補上推送的迭代,那一則推送同樣經 FR-003 沿用。
3. **假如**使用者變更執行階段類型或結束後開了新的工作階段,**當**第一次打開模型目錄,**則**系統重新讀一次顯示記憶體總量,不沿用上一個工作階段的值。
4. **假如**讀顯示記憶體時 `colab exec` 失敗、逾時,或成功但讀到的顯示記憶體總量是 null,**當**使用者打開模型目錄,**則**UI API 回 200,`vramBytes` 與每個模型的 `mayNotFit` 為 null,模型清單照常列出;下一次打開時再讀一次。
5. **假如**上一次讀顯示記憶體失敗、這一次讀到了總量,**當**使用者之後再打開模型目錄,**則**沿用這一次讀到的值,不再跑 `colab exec`。
6. **假如**工作階段經過重連中又接回(同一個工作階段),**當**使用者打開模型目錄,**則**沿用之前讀到的值。

**功能需求**:

- **FR-003**:模型目錄的顯示記憶體總量,系統必須在每個工作階段只經 `colab exec` 成功讀到一次(讀到的是數字);同一個工作階段之後列出目錄(打開模型目錄、推送 `models.updated`、預先載入前確認目錄)一律沿用讀到的值;這一輪推送 `models.updated` 的只有預先載入結束時(下載完成時不推送,001 完成報告 Q188、Q192)。
- **FR-004**:讀顯示記憶體時 `colab exec` 失敗、逾時,或成功但顯示記憶體總量為 null,系統必須照 001 `ui.openapi.yaml` § listCatalog 回 `vramBytes` 與 `mayNotFit` 為 null 並照常列出模型,不保留這次的結果,下一次列出目錄時再讀。
- **FR-005**:工作階段換了(開新的工作階段、變更執行階段類型)時,系統必須在新工作階段第一次列出目錄時重新讀取,不得沿用前一個工作階段的值;同一個工作階段重連接回時沿用。

**非功能需求**:

- **NFR-002**:同一個工作階段讀過顯示記憶體之後,打開模型目錄的回應時間不得再包含 `colab exec` 的時間(門檻見 SC-002)。

### 邊界情況

- 佇列裡同名的那筆已經下載完成:它已經出現在執行環境的模型清單,由「已下載」的檢查擋下;佇列紀錄本身不算「已在佇列」。
- 佇列裡同名的那筆下載失敗:不算在佇列中,可以再加入一筆(使用者故事 1 驗收情境 7)。
- 寫了版本的名稱(例如 `qwen2.5:7b`)照原樣比對,不補任何東西;不同版本不算重複。
- `colab exec` 成功但顯示記憶體總量讀到 null(執行環境上的 `nvidia-smi` 失敗或逾時):這個系統開的執行環境都有 GPU(001 `ui.openapi.yaml` 的 `GpuType` 只有 T4、L4、G4、A100、H100),null 視同讀取失敗,照 FR-004 回 null、不快取,下一次列出目錄時再讀。
- 後端重新啟動後接回同一個工作階段:快取只在記憶體裡,重新啟動後第一次列出目錄會再讀一次。
- 試算或加入下載時沒有就緒的工作階段:照 001 回 503 `NO_READY_SESSION`;重複檢查需要讀執行環境上的模型清單,沒有工作階段時不做。

### 非功能需求

- **NFR-003**(適用:使用者故事 1、2):這兩條路徑(重複的模型名稱、讀不到顯示記憶體)上任何一種情況,UI API 都不得回 500;回應的狀態碼、`code` 與欄位都照 001、002 的 `ui.openapi.yaml`。

## 關鍵實體

- **模型名稱(ModelName)**:使用者輸入或勾選的官方模型名稱,可帶 `:版本`。屬性:名稱、版本(沒寫時視為 `latest`)、補過版本後的完整名稱。重複判定一律用補過版本後的完整名稱。
- **顯示記憶體快取(VramCache)**:一個工作階段讀到的 GPU 顯示記憶體總量。屬性:工作階段名稱、顯示記憶體總量(位元組;只存讀到的數字,讀到 null 時不存)。不存讀取時間:沒有任何需求依讀取時間失效,換工作階段才失效(FR-005)。只活在後端記憶體裡,跟著工作階段換掉。

## 成功標準 *(必填)*

### 可衡量成果

- **SC-001**:沒寫版本與寫了 `latest` 的名稱,和「已下載」「排隊中」「下載中」「同一批」四種情況的每個組合,試算與加入下載回的狀態碼與 `code` 100% 符合 001 `ui.openapi.yaml`;佇列裡同時是排隊中或下載中的同名項目 0 筆;0 個組合回 500。
- **SC-002**:讀顯示記憶體的替身每次延遲 3 秒時,同一個工作階段連續打開模型目錄 10 次,`colab exec` 只執行 1 次,第 2 次起每次 `GET /api/models` 在 1 秒內回應。
- **SC-003**:讀顯示記憶體失敗、逾時或讀到 null 時,`GET /api/models` 100% 回 200 且 `vramBytes` 為 null;下一次打開時 `colab exec` 再執行 1 次。

## 假設

- 錯誤代碼、HTTP 狀態碼與欄位全部沿用 001 與 002 的 `ui.openapi.yaml`;409 的 `model` 用補過版本的名稱,和 002 `LIBRARY_*` 錯誤帶的 `model` 一致。這一輪不改合約、不改 UI。
- 版本的大小寫照原樣比對,不另外正規化(合約的 `ModelName` 名稱部分只允許小寫)。
- 補 `latest` 的規則和精選清單用的是同一條(002 完成報告「下一步」);要不要抽成共用由系統分析決定,精選清單的行為不變。
- 快取只放顯示記憶體總量;試算與加入下載用的剩餘磁碟空間會隨下載變動,每次照讀,不快取。
- 快取放在後端記憶體,不存表;後端重新啟動後重新讀一次。
- 讀顯示記憶體失敗或讀到 null 時不另外寫後端日誌,沿用 001 的日誌規則;維護的人從 `vramBytes` 為 null 看得出沒讀到,要知道原因就再打開一次模型目錄重現。
- 試算新增的「已下載」檢查要讀執行環境上的模型清單;連不到遠端 Ollama、回應格式不對或逾時,照 001 `ui.openapi.yaml` § estimateDownloads 回 502 `OLLAMA_UNREACHABLE`、`OLLAMA_BAD_RESPONSE` 或 504 `OLLAMA_TIMEOUT`,和加入下載相同。
- 同時發生的第一次讀取(例如打開模型頁的同時預先載入結束、推送 `models.updated`)不保證合併成一次,可能各跑一次 `colab exec`;之後都沿用。
- 驗收以替身進行(遠端 Ollama、`colab exec` 都用替身),不開 Colab、0 compute units;真環境的耗時 001 已量過(Q179)。
- 不在範圍內:G-02 的超時(002 plan.md Q22)、預先載入用沒寫版本的名稱指名、預先載入無效(001 完成報告)、001 完成報告列的其他 Q178、Q203 項目。
