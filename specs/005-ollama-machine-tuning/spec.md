# 功能規格:依機器配置調整遠端 Ollama 的設定,並在 UI 顯示與調整

**功能分支**:`005-ollama-machine-tuning`

**建立日期**:2026-11-15

**狀態**:草稿

**輸入**:使用者描述:「我想確認目前 ollama 有沒有開平行處理……如果我未來要測試模型能力,能不能一次回答多題……加快測試速度……能否對 A100 時 GPU RAM 比較大做優化……應該說對不同配置的機器做優化……然後我還希望在 UI 上改動。」

## 使用者情境與測試 *(必填)*

### 使用者故事 1 - 開好工作階段,遠端 Ollama 就依這台機器的顯示記憶體調好設定(優先順序:P1)

使用者開一個工作階段(T4、L4、G4 或 A100),不用設定任何東西;執行環境就緒時,遠端 Ollama 已經依這台機器量到的顯示記憶體,用對應級距的平行數、context 長度與同時載入模型數啟動。區網的測試程式同時送多題時,大顯示記憶體的機器會同時處理,總耗時比一題一題排隊短。工作階段頁顯示這台機器量到的顯示記憶體、系統記憶體與實際套用的設定。

**為何是這個優先順序**:這是使用者「加快測試速度」的核心,只做完這個故事,A100 等大顯示記憶體的機器就不再閒置大部分顯示記憶體;後兩個故事都是在它之上的調整。

**獨立測試**:用替身的 Colab 執行環境,分別回報顯示記憶體 6、15、22.5、40、96 GB 與讀不到 → 開工作階段到就緒 → 確認遠端 `ollama serve` 啟動時帶的環境變數符合 FR-002 的級距(讀不到時只帶原本的兩個),UI API 的工作階段狀態與工作階段頁顯示同一組設定。

**驗收情境**:

1. **假如**使用者開一個 A100 的工作階段,執行環境量到顯示記憶體 40 GB,**當**工作階段就緒,**則**遠端 Ollama 以平行數 8、context 長度 8192、同時載入模型數 2 啟動,flash attention 與 KV cache `q8_0` 開啟,工作階段頁顯示「顯示記憶體 40 GB · 平行 8 · context 8192 · 同時載入 2 個模型(自動)」。
2. **假如**使用者開一個 T4 的工作階段,量到顯示記憶體 15 GB,**當**工作階段就緒,**則**套用平行數 2、context 長度 4096、同時載入模型數 1。
3. **假如**執行環境讀不到顯示記憶體(`nvidia-smi` 失敗或逾時),**當**工作階段就緒,**則**遠端 Ollama 照 004 的方式啟動(只帶 `OLLAMA_HOST`、`OLLAMA_ORIGINS`),工作階段頁顯示「讀不到顯示記憶體,使用 Ollama 預設值」,工作階段照常就緒。
4. **假如**工作階段已就緒,**當**使用者到工作階段紀錄看這一筆,**則**紀錄裡有這次量到的顯示記憶體與套用的設定。
5. **假如**後端在工作階段就緒期間重新啟動,**當**後端恢復這個工作階段,**則**工作階段頁仍顯示同一組設定,不重新量測、不重啟遠端 Ollama。

**功能需求**:

- **FR-001**:啟動遠端 Ollama 之前,系統必須在執行環境上讀取第一張 GPU 的顯示記憶體總量與系統記憶體總量。
- **FR-002**:系統必須依量到的顯示記憶體總量,照下列級距決定遠端 Ollama 的設定,以環境變數 `OLLAMA_NUM_PARALLEL`、`OLLAMA_CONTEXT_LENGTH`、`OLLAMA_MAX_LOADED_MODELS` 帶給 `ollama serve`;級距(平行數/context 長度/同時載入模型數)為:未滿 12 GiB 為 1/4096/1;12 GiB 以上、未滿 20 GiB 為 2/4096/1;20 GiB 以上、未滿 32 GiB 為 4/8192/1;32 GiB 以上、未滿 64 GiB 為 8/8192/2;64 GiB 以上為 16/8192/3。每一級都另外帶 `OLLAMA_FLASH_ATTENTION=1` 與 `OLLAMA_KV_CACHE_TYPE=q8_0`。判斷只看顯示記憶體總量,不看 GPU 類型名稱。

- **FR-003**:讀不到顯示記憶體、而且這次沒有手動覆蓋值(使用者故事 2)時,系統必須不帶 FR-002 的任何環境變數,照 004 的方式啟動遠端 Ollama,並把這次標成「讀不到顯示記憶體,使用 Ollama 預設值」;不得因此讓開啟失敗。
- **FR-004**:系統必須在工作階段狀態裡提供這次量到的顯示記憶體、系統記憶體、實際套用的三項設定,以及每一項是自動值還是手動覆蓋;工作階段頁必須顯示這些資訊。
- **FR-005**:系統必須把量到的顯示記憶體與實際套用的設定記進工作階段紀錄。

**非功能需求**:

- **NFR-001**:讀取顯示記憶體與系統記憶體不得讓開啟工作階段的時間比 004 多超過 5 秒(門檻見 SC-003)。

### 使用者故事 2 - 開啟前手動覆蓋設定,並依 GPU 類型記住(優先順序:P2)

使用者想比較不同設定的速度,或覺得自動值不適合手上的模型,在開工作階段的畫面展開「Ollama 設定」,手動填平行數、context 長度或同時載入模型數;留空的項目用自動值。填過的值依 GPU 類型記住,下次開同一種類型時預先填好,也可以一鍵清掉、回到全部自動。

**為何是這個優先順序**:自動級距是估算,使用者要測試、比較時需要自己指定;記住覆蓋值讓試出來的值不用每次重填。沒有這個故事,故事 1 仍然可以獨立使用。

**獨立測試**:開啟畫面選 A100,填平行數 4、其他留空 → 開到就緒 → 確認遠端以平行數 4、context 與同時載入模型數為自動值啟動,工作階段頁標出平行數是手動 → 結束後再開,選 A100 時平行數預先填 4,選 T4 時是空的 → 按「全部改回自動」再開,三項都是自動值。

**驗收情境**:

1. **假如**使用者在開啟畫面選 A100、展開「Ollama 設定」,**當**只填平行數 4 並開啟,**則**遠端 Ollama 以平行數 4、context 長度 8192、同時載入模型數 2 啟動,工作階段頁把平行數標為「手動」、其他兩項標為「自動」。
2. **假如**上一次開 A100 時覆蓋了平行數 4,**當**使用者再開啟畫面選 A100,**則**平行數預先填 4;改選 T4 時,三個欄位顯示 T4 自己記住的值,沒有記過就是空的。
3. **假如**A100 記住了覆蓋值,**當**使用者在開啟畫面按「全部改回自動」並開啟,**則**三項都用自動值,A100 記住的覆蓋值清空。
4. **假如**使用者在平行數填 64,**當**按開啟,**則**系統擋下,說明平行數要在 1~32 之間,不開工作階段、不記住這個值。
5. **假如**使用者選了 A100 並覆蓋平行數 4,執行環境卻讀不到顯示記憶體,**當**工作階段就緒,**則**平行數照覆蓋值 4 套用,其他兩項不帶、用 Ollama 預設值。

**功能需求**:

- **FR-006**:開啟工作階段的畫面必須提供「Ollama 設定」區塊,可以分別填平行數、context 長度與同時載入模型數;留空的項目用 FR-002 的自動值,欄位旁顯示「留空 = 自動」。
- **FR-007**:開啟工作階段時,系統必須把填了的項目覆蓋 FR-002 的自動值帶給遠端 Ollama,沒填的項目照 FR-002;讀不到顯示記憶體時,只帶填了的項目與 `OLLAMA_FLASH_ATTENTION`、`OLLAMA_KV_CACHE_TYPE`。
- **FR-008**:開啟畫面選一種 GPU 類型時,系統必須把這種類型記住的覆蓋值預先填進三個欄位;沒有記過的欄位留空。
- **FR-009**:開啟畫面必須提供「全部改回自動」,清空三個欄位;用清空後的欄位開啟時,系統必須清除這種類型記住的覆蓋值。

**非功能需求**:

- 無

### 使用者故事 3 - 工作階段開著時改設定,重啟遠端 Ollama 套用(優先順序:P3)

使用者在工作階段就緒時想換一組設定試速度,在工作階段頁改平行數、context 長度或同時載入模型數並套用;系統重啟遠端 Ollama,已載入的模型重新載入,不用結束、重開工作階段、重新下載模型。有下載、UI 對話或區網程式的請求還在進行時,系統擋下並說明要等它們結束。

**為何是這個優先順序**:開著時改設定是比較設定最快的方式,但必須先有故事 1 的設定機制,故事 2 的記住機制也會用到;沒有它,使用者仍可結束再開來換設定,只是比較慢。

**獨立測試**:替身工作階段就緒、已載入模型 A → 在工作階段頁把平行數改成 4 並套用 → 確認遠端 Ollama 以新設定重啟、A 重新載入、工作階段回到就緒且顯示新設定,這種類型記住的覆蓋值變成 4 → 讓一個相容端點的請求在進行中再改一次,確認被擋下、遠端沒有重啟 → 讓替身的重啟失敗,確認改回自動值重啟成功、畫面說明手動設定沒套用、記住的值沒有變。

**驗收情境**:

1. **假如**工作階段就緒、已載入模型 A,沒有任何下載或請求在進行,**當**使用者在工作階段頁把平行數改成 4 並按「套用並重啟 Ollama」、確認,**則**系統重啟遠端 Ollama 套用新設定,重新載入 A,工作階段回到就緒,工作階段頁顯示平行數 4(手動)。
2. **假如**套用的確認視窗打開,**當**使用者閱讀說明,**則**說明寫出「會重啟遠端 Ollama,已載入的模型要重新載入,這段時間無法對話與送請求」。
3. **假如**下載佇列有一個模型正在下載,**當**使用者按套用,**則**系統擋下,說明「有模型正在下載,下載完才能套用」,遠端 Ollama 沒有重啟,下載不中斷。
4. **假如**UI 對話框正在回應,或區網程式經相容端點送的請求還沒回完,**當**使用者按套用,**則**系統擋下,說明有請求還在進行、要等它們結束,遠端 Ollama 沒有重啟。
5. **假如**套用成功,**當**使用者下次開同一種類型的工作階段,**則**開啟畫面預先填好這次套用的值。
6. **假如**新設定讓遠端 Ollama 起不來,**當**系統偵測到重啟失敗,**則**系統改用 FR-002 的自動值再重啟一次;成功的話工作階段回到就緒,工作階段頁說明「手動設定沒有套用成功,已改回自動值」,這種類型記住的覆蓋值不寫入這組失敗的值。
7. **假如**改回自動值也重啟失敗,**當**系統偵測到,**則**工作階段照 001 的失聯處理。
8. **假如**系統正在重啟遠端 Ollama,**當**區網程式經相容端點送請求,**則**回應和 001 工作階段未就緒時相同的錯誤,不排隊等待。

**功能需求**:

- **FR-010**:工作階段就緒時,工作階段頁必須可以修改三項設定並「套用並重啟 Ollama」,套用前必須有確認步驟,說明會重啟遠端 Ollama、已載入的模型要重新載入。
- **FR-011**:有模型正在下載,或 UI 對話框與相容端點有還沒回完的請求時,系統必須拒絕套用,說明原因,不重啟遠端 Ollama、不中斷下載與請求。
- **FR-012**:套用時,系統必須以新設定重啟遠端 Ollama,重啟期間工作階段不算就緒,重啟完成後重新載入重啟前已載入的模型,再回到就緒。
- **FR-013**:新設定重啟失敗時,系統必須改用 FR-002 的自動值再重啟一次;成功時回到就緒並在工作階段頁說明手動設定沒有套用成功,失敗時照 001 的失聯處理。
- **FR-014**:套用成功時,系統必須把這次的值寫成這種類型記住的覆蓋值;改回自動值的情況(FR-013)不寫入。

**非功能需求**:

- **NFR-002**:從確認套用到工作階段回到就緒(不含重新載入模型的時間),必須在 90 秒內完成(門檻見 SC-004)。

### 邊界情況

- 量到的顯示記憶體剛好落在級距邊界(例如 L4 的 22.5 GiB、某台剛好 32 GiB):照 FR-002 的「以上、未滿」判斷,32 GiB 屬於 32~64 那一級。
- 執行環境有多張 GPU:只看第一張,與 001 `probe_resources.py` 的做法相同。
- 變更執行階段類型(001 使用者故事 1 驗收情境 12):新的執行環境重新量測,套用新類型記住的覆蓋值或自動值,不沿用舊類型的設定。
- 後端在遠端 Ollama 重啟到一半時停機:後端恢復時照 001 的恢復流程判斷工作階段狀態,工作階段頁顯示恢復後讀到的設定。
- 填了覆蓋值,但數值和自動值相同:仍標為「手動」並記住,使用者明確填的值不因剛好相同而變成自動。
- 已經有 `--env` 指定的同名環境變數:以系統這次決定的值為準,同一個變數不得同時出現兩個值。

## 全域需求 *(必填)*

### 功能需求

- **FR-015**(適用:使用者故事 2、3):手動填的值必須在固定範圍內:平行數 1~32、context 長度 2048~131072、同時載入模型數 1~4,而且都要是整數;超出範圍時系統必須擋下並說明該項的範圍,不開啟或不套用、不記住這個值。系統不估算這組值放不放得進顯示記憶體。
- **FR-016**(適用:使用者故事 2、3):覆蓋值必須依 GPU 類型(T4、L4、G4、A100、H100)分別記住,跨工作階段與後端重新啟動保留;只記填了的項目,沒填的項目維持自動。

### 非功能需求

- **NFR-003**(適用:使用者故事 1、2、3):設定的讀取、顯示與套用不得對桌機 127.0.0.1:11434 送任何請求,也不得在 UI、紀錄或 log 印出 token 與轉發位址(沿用 001 對本機 Ollama、token 與轉發位址的規定)。

## 關鍵實體

- **機器量測(MachineProbe)**:開啟工作階段時在執行環境上量到的硬體資訊。屬性:顯示記憶體總量(讀不到時為空)、系統記憶體總量、GPU 名稱、量測時間。屬於一個工作階段。
- **Ollama 設定(OllamaTuning)**:這次實際帶給遠端 Ollama 的設定。屬性:平行數、context 長度、同時載入模型數、flash attention、KV cache 類型,每一項的來源(自動、手動、Ollama 預設)、是否因重啟失敗改回自動值。屬於一個工作階段,由機器量測與類型覆蓋值決定。
- **類型覆蓋值(RuntimeTypeTuningOverride)**:某一種 GPU 類型記住的手動值。屬性:GPU 類型、平行數、context 長度、同時載入模型數(各自可為空,空的代表自動)、最後更新時間。每種類型最多一筆。

## 成功標準 *(必填)*

### 可衡量成果

- **SC-001**:在真的 A100 工作階段,用同一個 7B 模型、同一批 16 題短答題目同時送出,自動值的總耗時不超過平行數 1 時的 60%。
- **SC-002**:在真的 T4 工作階段做 SC-001 的同一個量測,自動值的總耗時不超過平行數 1 時的 85%;兩台都要在 `ollama ps` 看到模型 100% 在 GPU。
- **SC-003**:開啟工作階段到就緒的時間,和 004 的同類型量測相比增加不超過 5 秒。
- **SC-004**:開著時套用新設定,從確認到回到就緒(不含重新載入模型)在 90 秒內;10 次套用都不中斷任何進行中的下載或請求(進行中時都被擋下)。
- **SC-005**:替身測試涵蓋 FR-002 的五個級距、每個級距的上下邊界與讀不到顯示記憶體,套用的設定 100% 符合級距表。

## 假設

- FR-002 的級距與數值是依 7B~32B 模型、KV cache `q8_0` 估算的初始值,technical-research 與 SC-001、SC-002 的實測可以修正;修正後以修正的值為準,本 spec 要同步更新。
- flash attention 與 KV cache `q8_0` 每一級都固定開啟,UI 只顯示、不開放修改(使用者本人決定只開放三項數值)。
- 系統記憶體只量測、顯示與記錄,不影響級距;Colab 的高 RAM 選項照 001、004 的做法。
- 範圍只有本系統在 Colab 上啟動的遠端 Ollama;桌機上使用者自己的 Ollama(127.0.0.1:11434)不在範圍內,也不會被讀取或修改。
- 在 UI 一次貼多題、同時送出的批次測試介面不在這次範圍;同時送多題由使用者的區網程式經相容端點做。
- 相容端點本身不限制同時轉發的請求數;如果 technical-research 發現有限制,要一起放寬到不低於 FR-015 的平行數上限。
- 實測(SC-001~SC-004 在真的 Colab 上的部分)每一次都要先停下問使用者本人並在場,照 001 testplan 的 P1~P9。
