- `box.run(steps)` 起一個子行程 `sys.executable -I -c …` 模擬 Colab kernel:每一步照 CLI 的 `_build_env_prelude` 先 `os.environ[KEY] = VALUE`,再 `runpy.run_path(<腳本>, run_name="__main__")`,收下那一步 stdout 最後一個 `CGB-RESULT ` 行與耗時;全部跑完印出 kernel 的 `os.environ`。一步的環境是 `PATH`、`HOME`、`OLLAMA_MODELS`、`OLLAMA_HOST=127.0.0.1:<port>`、`OLLAMA_ORIGINS=*`、三個 `CGB_TUNE_*`(沒指定的代入空字串)、上面的覆寫變數(`CGB_INSTALL_COMMAND=true`,三個秒數案例有寫才改)與 `CGB_TEST_MARKER=<uuid>`。子行程在 `runpy` 之前替 `socket.socket.connect` 裝上守門:只放行 `127.0.0.1:<port>`,其他位址一律丟 `ConnectionRefusedError` 並記進 `box.blocked`;每支測試結束時斷言 `box.blocked` 是空的(護欄 P6,US1-CLI-17 另有明確的則)。
- `box.start_old_serve(via="/usr/local/bin/ollama", with_child=False, child_ignores_term=False)` 由測試自己以 `start_new_session=True` 起一個舊的 serve(模擬 001~004 或上一次啟動的那一個),`with_child` 時同一個行程群組另有一個 `sleep 300`(代表載入模型的 `llama-server`),`child_ignores_term` 時那個成員忽略 SIGTERM;回傳 serve 與成員的 pid。
- 觀察:`box.serve_env(pid)` 讀 `/proc/<pid>/environ` 成 (名稱, 值) 清單(重複的名稱會出現兩次);`box.pid_file()`、`box.state()` 讀 pid 檔與狀態檔(不存在回 None);`box.version()` 以 `httpx` 打 `http://127.0.0.1:<port>/api/version`(送之前斷言 port 不是 11434~11436、8780);`box.marked()` 列出 `/proc/*/environ` 含這支測試 `CGB_TEST_MARKER` 的行程。
- 收尾:對 `box.marked()`、pid 檔裡的 pid 與 `start_old_serve` 起的行程逐一對行程群組送 SIGTERM,10 秒內沒結束就 SIGKILL,再斷言行程與行程群組都已結束;不碰 `box.marked()` 以外、也不是這支測試起的行程。

下面說「量到 X MiB」就是 `box.fake_gpu(lines=[(<名稱>, X)])`;「新啟動」是 serve 還沒在回應、腳本走安裝(`CGB_INSTALL_COMMAND=true`)與啟動;「已在執行」是先以 `box.start_old_serve()` 起好、狀態檔照案例寫好。期望值裡的 GiB 換算是 MiB × 1048576。

這一節新增的 helper(故事 2、3 的 E2 節沿用):

### 3.2 E2 後端 UI API(FastAPI REST 與 SSE)

整合案例寫進 `tests/integration/test_api_tuning.py`(和故事 1 同一檔),單元案例寫進 `tests/unit/test_tuning.py`;分隔註解寫 `# ---- 005 US2-API-NN`。沿用故事 1 E2 節的 `GIB`、`A100`、`L4`、`applied`、`started`、`T4_STARTED`、`A100_STARTED`、`record_of`、`sent_overrides` 與它列的共用件,以及 `test_api_session.py` 的 `ColabWorld`、`open_ready`、`wait_for_state`、`wait_until`、`error_code`、`T4`,`test_api_recovery.py` 的 `running`。

這一節新增的 helper(故事 3 的 E2 節沿用):

- `tuning_body(np, ctx, mlm)` 回 `{"numParallel": np, "contextLength": ctx, "maxLoadedModels": mlm}`;`NONE3 = tuning_body(None, None, None)`。
- `open_with(client, runtime_type, tuning)` 送 `POST /api/session`,本文 `{"runtimeType": runtime_type, "tuning": tuning}`,回傳回應(不等就緒)。
- `overrides(client)` 回 `GET /api/tuning/overrides` 的 `items` 轉成以 `gpu` 為鍵的 dict;`remember(client, gpu, tuning)` 以 `open_with` 開那一種類型到就緒再 `DELETE /api/session` 等 `ended`,讓那種類型記住 `tuning`,回傳那一次受理時的 `fake_clock.now()`。
- `log_out(fakes)`:`fakes.colab.get_usage.raises("AUTH_REQUIRED")`,照 001 `test_沒有授權時開啟要先登入_不呼叫_CLI_開機` 讓授權檢查判成未登入。

類型覆蓋值的寫入時機照 Q9(受理時寫、開啟失敗不還原)、清除照 Q8、Q23(三個 null 開啟時清除,`updatedAt` 變成 null)。範圍檢查的每個邊界在單元案例 US2-API-16~22 驗;整合案例只驗 api 有接上同一個檢查、檢查的順序,以及被擋下時沒有寫入、沒有開啟。

### 3.3 E4 資料庫(SQLite)

本節驗類型覆蓋值在 `runtime_type_tunings` 這一側的事實(FR-018 的儲存):每種 GPU 類型最多一列、只記填了的項目、範圍的最後一道 CHECK(FR-017)、清除時刪列而不留三個 NULL 的列(Q23)、跨後端重新啟動保留(`contracts/store.dbml` § `Table runtime_type_tunings` 與開頭「寫入的時機」)。什麼時候寫、整份取代、開啟失敗不還原(Q9)、套用成功才寫(FR-014)、清除時由誰刪,是 repos 與 E2 的事,本節只驗 schema 讓這些做法做得到、錯的做法寫不進去。遷移的交易與新舊庫的分辨由故事 1 的 E4 節測。

測試檔、分隔註解(`# ---- 005 US2-DB-NN`)、連線、「全新庫」「v1 舊庫」的建法與 helper 照故事 1 E4 節的說明。「情況 A」是全新庫;「情況 B」是 `_build_v1` 建出空的 v1 舊庫再跑 `create_schema` 遷移到 2 的庫;兩種情況以 `pytest.mark.parametrize` 跑同一組斷言(照 004 `_open_db` 的做法,`kind` 加 `from_v1`)。`updated_at` 一律寫 ISO 8601 UTC 字串。2026-11-15 以 `uv run python` 實測:`CHECK (num_parallel BETWEEN 1 AND 32)` 收下字串 `'4'`(INTEGER 親和性轉成 4)與 `'4.5'`(存成 REAL 4.5),所以下面的案例不拿這兩種當不合法的值;非整數由 api 先擋(FR-017),不是資料庫的責任。
