# 功能規格:佇列隨工作階段清空、測試對話框、Hugging Face 模型來源與可編輯的精選清單

**功能分支**:`004-chat-hf-curated-queue`

**建立日期**:2026-11-14

**狀態**:草稿

**輸入**:使用者描述:「首先第一點的話是它的下載佇列的話應該要隨著執行階段的關閉而清除才對,不然會留下很多之前的下載紀錄,這樣我也不知道這個模型到底下載了沒,我覺得這些資訊都過時了。第二點的話是我希望可以加一個測試用的對話框,讓我可以跟這個模型對話,看一下這個模型的一些基本能力等等。第三點的話是 Ollama 官方模型庫其實有點舊,我覺得還需要加上 Hugging Face 的,因為現在有很大一部分的模型直接放在那裡。第四點的話是精選清單應該要可以透過 UI 來做設定,這樣我才可以在下一次的工作執行階段前就先選好要下載的模型。5. H100 可以隱藏,因為目前看起來都沒有開放。」

## 使用者情境與測試 *(必填)*

### 使用者故事 1 - 工作階段結束後,下載佇列不留舊紀錄(優先順序:P1)

使用者結束工作階段(或工作階段被閒置自動結束、失聯、開啟失敗)之後,下載頁的佇列是空的;下一次開好工作階段時,佇列裡不會再出現上一台執行環境的「完成」「失敗」紀錄,讓他誤以為新的執行環境上已經有那個模型。

**為何是這個優先順序**:每台新的執行環境都是空的,上一台留下的「完成」紀錄是錯的資訊;這是使用者真的會被誤導的地方,改動也最小,只做完這個故事就能消掉「不知道到底下載了沒」。

**獨立測試**:工作階段就緒(替身)→ 佇列裡放一筆完成、一筆失敗、一筆排隊中 → 結束工作階段 → 確認 UI API 列出的佇列是空的、畫面上的佇列不用重新整理就清空 → 再開一個工作階段,佇列仍是空的,沒有自動開始任何下載。

**驗收情境**:

1. **假如**佇列裡有完成、失敗與排隊中的項目,**當**使用者按「結束」並確認,**則**工作階段結束後佇列沒有任何項目,下載頁的佇列不用重新整理就變成空的。
2. **假如**有一個模型正在下載,**當**工作階段結束或失聯,**則**下載中斷,那一筆和其他項目一起清除,不以「可用」出現在任何目錄(維持 001 使用者故事 3 驗收情境 7)。
3. **假如**工作階段被閒置自動結束、被 Colab 收回或重連逾時而失聯、或開啟失敗,**當**系統把它標成結束類的狀態,**則**佇列同樣清空。
4. **假如**工作階段「就緒」且已載入模型 A,佇列裡另有完成的項目,**當**使用者變更執行階段類型並確認,**則**舊工作階段的項目清除,只留下為了重新載入 A 而排入的那一筆,新的工作階段就緒後照 001 的變更類型流程下載並載入 A。
5. **假如**上一個工作階段結束時本系統的後端沒有在執行(例如在後端停機期間被 Colab 收回),**當**後端重新啟動並判定那個工作階段已結束,**則**佇列同樣清空。

**功能需求**:

- **FR-001**:工作階段進入已結束、開啟失敗或失聯時,系統必須清除下載佇列中的所有項目(完成、失敗、排隊中,以及因結束而中斷的下載中項目),並通知 UI 移除這些項目。
- **FR-002**:變更執行階段類型(001 使用者故事 1 驗收情境 12)時,為了在新工作階段重新載入原本已載入的模型而排入的項目,系統必須保留並在新工作階段就緒後下載;舊工作階段的其他項目照 FR-001 清除。
- **FR-003**:後端重新啟動時,若判定先前的工作階段已在停機期間結束,系統必須照 FR-001 清除佇列,不把上一台執行環境的項目帶到下一個工作階段。

**非功能需求**:

- **NFR-001**:工作階段結束後,下載頁的佇列必須在不重新整理頁面的情況下清空(門檻見 SC-001)。

### 使用者故事 2 - 在 UI 裡跟模型對話,試它的基本能力(優先順序:P2)

使用者下載好模型之後,想先試試它好不好用:在 UI 的對話頁選一個執行環境上的模型,打幾句話,看它怎麼回、回得多快,不用另外打開區網的對話工具。

**為何是這個優先順序**:這是新的能力,讓使用者在 UI 裡就能判斷下載的模型值不值得留;但不影響工作階段與下載本身,排在修正誤導資訊的故事 1 之後。

**獨立測試**:工作階段就緒(替身),執行環境上有一個模型 → 打開對話頁、選這個模型、送出兩則訊息 → 確認回覆逐段出現、第二則回覆帶到第一則的上下文、每則回覆下方顯示耗時與每秒 token 數 → 按「清空」後對話消失 → 確認資料庫與日誌裡沒有對話內容,閒置倒數在送出時歸零。

**驗收情境**:

1. **假如**工作階段「就緒」且執行環境上有已下載的模型,**當**使用者在對話頁選一個模型、輸入訊息送出,**則**模型的回覆逐段出現在對話框,不必等整則回覆完成。
2. **假如**已經對話了一輪,**當**使用者再送出一則訊息,**則**模型回覆時帶著前面的對話內容(多輪對話)。
3. **假如**一則回覆完成,**當**使用者看那則回覆,**則**下方顯示這則花了多久與每秒產生幾個 token。
4. **假如**模型正在回覆,**當**使用者按「停止」,**則**回覆停在目前的內容,可以接著送下一則。
5. **假如**對話框裡已有內容,**當**使用者按「清空」或換一個模型,**則**對話內容清掉,從頭開始。
6. **假如**選的模型還沒載入,**當**使用者送出訊息,**則**系統先載入再回覆(和 001 使用者故事 3 驗收情境 3 相同),畫面顯示正在載入。
7. **假如**沒有「就緒」的工作階段,或執行環境上沒有已下載完成的模型,**當**使用者打開對話頁,**則**不能送出,畫面說明原因(沒有工作階段或還沒有模型)。
8. **假如**模型正在回覆,**當**工作階段中斷或模型服務回錯誤,**則**已收到的部分保留,畫面標示這則回覆中斷與原因,不顯示成正常完成。
9. **假如**閒置自動結束正在倒數,**當**使用者在對話框送出一則訊息,**則**閒置倒數歸零重算(和 001 使用者故事 4 經 Ollama 相容端點的請求一樣)。

**功能需求**:

- **FR-004**:系統必須在 UI 提供對話頁:從執行環境上已下載完成的模型中選一個,輸入訊息送出後,把模型的回覆逐段顯示出來;同一段對話送出的每一則都帶著前面的對話內容。
- **FR-005**:每則回覆完成後,系統必須在回覆下方顯示這則的耗時與每秒產生的 token 數。
- **FR-006**:系統必須讓使用者在回覆中途按「停止」中斷這則回覆,並讓使用者按「清空」清掉整段對話;換模型時對話也清空。
- **FR-007**:對話頁送出的每一則訊息,系統必須和經 Ollama 相容端點的請求一樣,重設閒置自動結束的倒數(001 使用者故事 4)。
- **FR-008**:沒有就緒的工作階段或執行環境上沒有已下載完成的模型時,對話頁必須不能送出並說明原因;回覆途中工作階段中斷或模型服務回錯誤時,必須保留已收到的部分並標示中斷與原因。

**非功能需求**:

- **NFR-002**:對話內容(使用者的訊息與模型的回覆)不得寫入本系統的資料庫與日誌,只存在瀏覽器頁面上;離開或重新整理頁面即消失。日誌照 001 的規則只記時間、模型、耗時與狀態碼。
- **NFR-003**:回覆必須逐段顯示,第一段內容出現的時間不因本系統轉送而比模型服務本身多等 0.5 秒以上(門檻見 SC-002)。

### 使用者故事 3 - 在 UI 編輯精選清單,開好工作階段就自動下載(優先順序:P2)

使用者在還沒開工作階段的時候,就在 UI 把常用的模型加進精選清單、寫上說明與建議的執行階段類型,並把想每次都有的那幾個設成「開好就自動下載」;按「開啟」之後,工作階段一就緒,這幾個模型就自動排進下載,不用每開一次就重新勾一次。

**為何是這個優先順序**:每台新的執行環境都是空的,故事 1 又讓佇列不再跨工作階段保留,「下次要下載什麼」就要有一個固定的地方先選好;排在故事 2 同一級,因為它讓每次開工作階段後少做一輪勾選,但不影響已經能用的手動下載。

**獨立測試**:沒有工作階段時,在 UI 新增兩個精選項目(一個設自動下載、一個不設)、修改其中一個的名稱與說明、刪除另一個既有項目 → 重新整理後內容仍在 → 開啟工作階段(替身)→ 就緒後佇列自動出現設了自動下載的那一個,沒設的沒有出現 → 讓剩餘空間放不下其中一個,確認放不下的被跳過,下載頁佇列上方的提示區列出它與原因,重新整理後提示仍在。

**驗收情境**:

1. **假如**沒有工作階段,**當**使用者在 UI 新增一個精選項目(名稱、說明與建議的執行階段類型,後兩者可以不填),**則**它出現在精選清單,重新整理或後端重新啟動後仍在。
2. **假如**精選清單有一個項目,**當**使用者修改它的名稱、說明或建議的執行階段類型,或刪除它(刪除前確認),**則**清單立即反映;修改後它在清單裡的順序不變。
3. **假如**使用者新增或修改後的名稱和清單裡另一項重複(沒寫版本視為 `latest` 後相同),**當**送出,**則**系統阻止並提示已在清單裡(照 001 `CURATED_DUPLICATE`)。
4. **假如**精選清單有三個項目,其中兩個設了「開好就自動下載」,**當**工作階段就緒,**則**這兩個依清單順序自動排進下載佇列並開始下載,沒設的不排。
5. **假如**設了自動下載的模型已經在執行環境上,或已經在佇列中(例如變更類型時為了重新載入而排入),**當**工作階段就緒,**則**不再重複排入。
6. **假如**設了自動下載的模型加起來超過執行環境的剩餘磁碟空間,**當**工作階段就緒,**則**依清單順序排入放得下的,放不下的跳過,UI 提示哪幾個因空間不足沒有排入。
7. **假如**設了自動下載的某個模型取不到大小(模型來源連不到、逾時或找不到這個模型),**當**工作階段就緒,**則**跳過那一個並在 UI 提示原因,其他照常排入。
8. **假如**工作階段經過重連中又接回(同一個工作階段),**當**狀態回到「就緒」,**則**不再重新排入自動下載。
9. **假如**設了自動下載的某個模型大小超過這台執行環境的顯示記憶體總量(例如 T4 上的 20 GB 模型),**當**工作階段就緒,**則**跳過那一個並提示「這台可能無法載入」,其他照常排入;讀不到顯示記憶體總量時照常排入,不因此跳過。
10. **假如**自動下載排入了一些、跳過了一些,**當**使用者在工作階段就緒之後才打開下載頁(或重新整理),**則**佇列上方的提示區仍列出這次自動排入幾個、跳過哪幾個與原因,直到工作階段結束或使用者按關閉。

**功能需求**:

- **FR-009**:系統必須讓使用者在 UI 新增、修改與刪除精選清單的項目,不需要有工作階段;新增與修改可以填名稱、說明與建議的執行階段類型(001 `CuratedModelInput` 的三個欄位),修改不改變項目在清單裡的順序;刪除前必須確認。
- **FR-010**:系統必須讓使用者把精選清單的每一項設定為「開好就自動下載」或取消這個設定。
- **FR-011**:每個工作階段第一次就緒時,系統必須依精選清單的順序,把設了自動下載、執行環境上沒有、也不在佇列中的模型排進下載佇列;同一個工作階段重連接回時不再重排。
- **FR-012**:自動下載的模型加總超過剩餘磁碟空間、某一項取不到大小,或某一項的大小超過這台執行環境的顯示記憶體總量(和 001 模型目錄標「可能無法載入」同一個判斷;讀不到顯示記憶體總量時不以此跳過)時,系統必須跳過那幾項、照常排入其他項目;並在下載頁佇列上方的提示區列出這次自動排入的數量、每個被跳過的模型與原因,這個提示保留到工作階段結束或使用者按關閉為止,重新整理頁面後仍在。

**非功能需求**:

- **NFR-004**:精選清單(含自動下載的設定)必須存在本系統掛載的資料夾,後端重新啟動與容器重建後仍保留(沿用 001 的「存在掛載的資料夾」要求)。

### 使用者故事 4 - 從 Hugging Face 找模型下載(優先順序:P3)

使用者在下載頁用關鍵字搜尋 Hugging Face 上的 GGUF 模型,展開一個模型看有哪些量化版本與大小,勾選後和官方模型庫的模型一起加入下載;下載好的模型和其他模型一樣出現在模型目錄,區網的程式與對話頁都能用。

**為何是這個優先順序**:擴大可以下載的模型範圍,但使用者現在已經能用官方模型庫,不會擋住基本使用;排在故事 1~3 之後。

**獨立測試**:工作階段就緒(遠端 Ollama 與 Hugging Face 都用替身)→ 在下載頁搜尋 `qwen` → 列出含 GGUF 的模型 → 展開一個,列出各量化版本與大小 → 勾選一個加入下載,試算顯示的大小與替身給的檔案大小一致 → 下載完成後出現在模型目錄 → 讓 Hugging Face 替身逾時,確認搜尋區顯示暫時無法搜尋,官方模型庫與直接輸入照常可用。

**驗收情境**:

1. **假如**使用者打開「下載模型」,**當**在「搜尋 Hugging Face」輸入關鍵字搜尋,**則**列出 Hugging Face 上含 GGUF 檔、公開可下載的模型。
2. **假如**搜尋結果有一個模型,**當**使用者展開它,**則**列出它可下載的量化版本與各自的大小,執行環境上已有的標示「已下載」。
3. **假如**使用者勾選了 Hugging Face 的一個量化版本和官方模型庫的一個模型,**當**按「加入下載」,**則**試算顯示兩者的總大小、剩餘磁碟空間與預估時間,確認後兩者在同一個佇列依序下載(和 001 使用者故事 3 驗收情境 10 相同)。
4. **假如**Hugging Face 的模型下載完成,**當**使用者打開模型目錄,或區網的程式經 Ollama 相容端點列出模型,**則**這個模型和其他模型一樣列出,可以預先載入、在對話頁選用、被區網的程式指名。
5. **假如**使用者搜尋的關鍵字沒有符合的 GGUF 模型,**當**搜尋完成,**則**顯示找不到,並提示可以換關鍵字或直接輸入名稱。
6. **假如**Hugging Face 連不到、逾時或回應格式看不懂,**當**使用者搜尋或展開版本,**則**搜尋區顯示暫時無法搜尋 Hugging Face,官方模型庫、精選清單與直接輸入名稱照常可用,UI API 不回 500。
7. **假如**使用者指定的 Hugging Face 模型需要登入或同意條款才能下載,或沒有 GGUF 檔,**當**試算或加入下載,**則**系統阻止加入並說明原因(這一輪不支援需要登入的模型),佇列不變。

**功能需求**:

- **FR-013**:系統必須在下載頁提供 Hugging Face 搜尋:以關鍵字列出 Hugging Face 上含 GGUF 檔、不需登入即可下載的模型,結果多於一頁時可以載入更多。
- **FR-014**:使用者展開一個 Hugging Face 模型時,系統必須列出它可下載的量化版本與各自的大小,執行環境上已有的標示為已下載;勾選的版本和官方模型庫的模型一起走 001 的試算與加入下載(總大小、剩餘空間、預估時間與空間不足時阻止)。
- **FR-015**:Hugging Face 的模型需要登入、同意條款才能下載,或沒有可下載的 GGUF 檔時,試算與加入下載必須阻止加入並說明原因,佇列不變。
- **FR-016**:Hugging Face 連不到、逾時、回錯誤或回應格式不符時,系統必須只讓 Hugging Face 的搜尋與版本清單顯示暫時無法使用,官方模型庫、精選清單與直接輸入名稱不受影響。

**非功能需求**:

- **NFR-005**:每一個對 Hugging Face 的請求逾時為 10 秒,和官方模型庫相同(沿用 002 的 10 秒逾時;門檻見 SC-004)。

### 使用者故事 5 - 開工作階段時不列出開不到的 H100(優先順序:P3)

使用者開啟工作階段、變更執行階段類型或設定精選項目的建議類型時,可選的 GPU 只剩 T4、L4、G4、A100,不再看到目前開不到的 H100,免得選了才發現開啟失敗。

**為何是這個優先順序**:只是把一個開不到的選項藏起來,不影響其他功能;改動很小,哪一輪做都可以。

**獨立測試**:打開首頁的開啟面板、變更類型的選單與精選清單編輯的建議類型選單 → 確認只列 T4、L4、G4、A100,開啟的預設仍是 T4 → 打開「紀錄」,以前用 H100 開過的紀錄(假資料)照常顯示 H100;建議類型是 H100 的既有精選項目(假資料)照常顯示 H100。

**驗收情境**:

1. **假如**目前沒有工作階段,**當**使用者打開開啟工作階段的類型選單,**則**只列出 T4、L4、G4、A100,沒有 H100,預設仍是 T4。
2. **假如**工作階段「就緒」,**當**使用者打開變更執行階段類型的選單,**則**同樣不列出 H100。
3. **假如**紀錄裡有以前用 H100 開過的工作階段,**當**使用者打開「紀錄」,**則**那筆照常顯示類型 H100。
4. **假如**精選清單有一個建議類型是 H100 的既有項目,**當**使用者打開精選清單或編輯其他項目的建議類型,**則**那一項照常顯示 H100,建議類型的選單不列 H100。

**功能需求**:

- **FR-017**:開啟工作階段、變更執行階段類型與精選項目建議類型的 UI 選單不得列出 H100;其餘類型與開啟的預設 T4 不變,紀錄與精選清單裡既有的 H100 照常顯示。

**非功能需求**:

- 無

### 邊界情況

- 工作階段開啟中使用者按「結束」、或開啟失敗:佇列照 FR-001 清空;這時精選清單的自動下載還沒觸發(只在就緒時觸發)。
- 變更執行階段類型時,為了重新載入而排入的模型同時也設了自動下載:新工作階段就緒時只下載一次(使用者故事 3 驗收情境 5)。
- 精選清單編輯時名稱不合法(不符官方模型名稱或 `hf.co/<作者>/<模型>[:<量化版本>]` 的格式):照 001 `INVALID_MODEL_NAME` 阻止並提示;新增時不向模型來源查證是否存在,存不存在在自動下載或手動加入時才知道(使用者故事 3 驗收情境 7)。
- 精選清單是空的,或沒有任何一項設自動下載:就緒時不排任何項目,也不提示。
- 自動下載的某一項已排入佇列後,使用者在同一個工作階段把它從精選清單刪除或取消自動下載:已排入的下載不受影響,照常下載。
- 對話頁選的模型在對話途中被下載佇列以外的方式移除(例如工作階段結束):照 FR-008 標示中斷;對話頁的模型清單在工作階段結束後變成空的。
- 對話頁與區網程式同時使用同一個模型:依 Ollama 本身的處理方式排隊與並行(沿用 001 假設),本系統不另外限制。
- 同一個 Hugging Face 模型用沒寫量化版本與寫了 `latest` 的名稱各加一次:視為同一個(FR-018,和 003 補 `latest` 後比對的規則相同)。
- 後端重新啟動時接回仍在運作的同一個工作階段:佇列不清除(工作階段沒有結束),自動下載不重排(同一個工作階段)。

## 全域需求 *(必填)*

### 功能需求

- **FR-018**(適用:使用者故事 3、4):精選清單、直接輸入名稱與下載都必須接受 Hugging Face 的模型名稱 `hf.co/<作者>/<模型>[:<量化版本>]`;沒寫量化版本視為 `latest`,和官方模型名稱一樣先補版本再做 003 的重複判定(已下載、已在佇列、同一批合併成一筆)。

### 非功能需求

- **NFR-006**(適用:使用者故事 1、2、3、4):這一輪新增或改變的路徑(清空佇列、對話、編輯精選清單、自動下載、Hugging Face 搜尋與下載)上任何一種錯誤,UI API 都不得回 500;回應的狀態碼與錯誤代碼沿用 001~003 的 `ui.openapi.yaml`,沒有對應代碼的由系統分析補進合約。
- **NFR-007**(適用:使用者故事 2、3、4):新增的畫面與提示文字一律為繁體中文(沿用 001 的介面語言要求),模型名稱與量化版本保留原文。

## 關鍵實體

- **下載項目(DownloadJob)**:沿用 001。多了一個規則:只屬於一個工作階段,工作階段結束時清除;唯一的例外是變更執行階段類型時為了重新載入而排入、要帶到新工作階段的項目。屬性新增:來源(官方模型庫或 Hugging Face)、加入原因(使用者、重新載入、自動下載)。
- **精選清單項目(CuratedModel)**:沿用 001(名稱、說明、建議的執行階段類型都可在 UI 編輯)。屬性新增:開好就自動下載(是或否,預設否)、排列順序(新增的順序,修改不變);名稱可以是官方模型名稱或 Hugging Face 名稱。
- **Hugging Face 模型(HfModel)**:Hugging Face 上一個含 GGUF 檔的公開模型。屬性:作者、模型名稱、量化版本清單(每個版本的名稱與大小)。不存表,每次查詢取得。
- **對話(ChatConversation)**:對話頁上的一段對話。屬性:選用的模型、依序的訊息(角色、內容)、每則回覆的耗時與每秒 token 數。只存在瀏覽器頁面上,不存表、不寫日誌。
- **自動下載結果(AutoDownloadResult)**:一個工作階段就緒時自動排入的結果。屬性:排入的模型、跳過的模型與原因(空間不足、取不到大小、這台可能無法載入)、使用者是否已關閉提示。保留到這個工作階段結束,重新整理頁面仍讀得到,不跨工作階段保留。

## 成功標準 *(必填)*

### 可衡量成果

- **SC-001**:每一種結束方式(使用者結束、閒置自動結束、被 Colab 收回、重連逾時、開啟失敗)後 5 秒內,UI API 列出的下載佇列為 0 筆,下載頁不重新整理即顯示為空;變更執行階段類型時,佇列只剩為了重新載入而排入的項目。
- **SC-002**:模型服務替身每 0.1 秒吐一段、共 20 段時,對話頁第一段出現的時間比替身吐出第一段多不超過 0.5 秒;每則回覆都顯示耗時與每秒 token 數;測試前後資料庫與日誌中出現對話內容的次數為 0。
- **SC-003**:精選清單設了自動下載的項目,在工作階段就緒後 30 秒內 100% 被排入佇列或在 UI 標示跳過原因;沒設的 0 筆被排入;同一個工作階段重連接回後重複排入 0 筆;就緒後才打開或重新整理下載頁時,跳過的模型 100% 仍列在提示區。
- **SC-004**:Hugging Face 在逾時內沒有回應時,搜尋與展開版本從送出到畫面顯示暫時無法搜尋在 11 秒內(10 秒逾時加 1 秒餘裕);期間官方模型庫的搜尋 100% 照常回應。
- **SC-005**:開啟、變更類型與精選項目建議類型的選單中出現 H100 的次數為 0;紀錄與精選清單中既有 H100 的項目 100% 照常顯示。
- **SC-006**:這一輪新增或改變的路徑上,所有驗收情境與錯誤情況中 UI API 回 500 的次數為 0。

## 假設

- 第一點(佇列清空)依使用者原話清除整個佇列,包含尚未開始的排隊中項目(使用者本人 2026-11-14 確認,見 `分身決策紀錄.md` D7);這修訂了 001 假設「工作階段結束時,佇列中尚未完成的項目保留在佇列,下次可繼續」與 001 邊界情況「佇列中未完成的項目保留,可再下載」。「下次要下載什麼」改由精選清單的自動下載承接(使用者故事 3)。
- 第二點(對話框)修訂了 001 假設「不做 UI 內的對話介面;使用模型一律透過 Ollama 相容端點」;區網程式使用模型的方式不變。
- 第三點(Hugging Face)修訂了 001 plan.md Q9「只取官方 `/library/`,不接受社群模型」與 001 `ui.openapi.yaml` 的 `ModelName` 格式;合約怎麼放寬由系統分析決定。只支援 Ollama 能直接下載的 GGUF 模型;需要登入、同意條款(gated)或私有的模型不在這一輪範圍,本系統不存 Hugging Face 的 token。
- 第五點(H100)修訂了 001 假設「可選的執行階段類型以 Colab CLI 支援的為準(含 H100)」中 UI 列出的部分;後端合約與資料庫的類型清單不變,只在 UI 選單隱藏。哪天 H100 開放了再另外加回。
- Hugging Face 的模型由執行環境上的 Ollama 直接從 Hugging Face 下載(走 001 的下載佇列),不經本系統所在的主機;Ollama 是否支援、大小怎麼取,由 technical-research 查證。
- 對話頁走本系統的後端轉送到目前的工作階段,不在瀏覽器直接連 Colab(維持 001「遠端模型服務不透過公開網址暴露」的要求);對話只做文字,不做圖片、檔案上傳、system prompt 與 temperature 等參數設定。
- 自動下載只在每個工作階段第一次就緒時觸發一次;剩餘空間與大小的判定沿用 001 試算的方式。自動下載開始的下載照常會讓執行環境多開一點時間,這和手動下載相同,不另外提示費用。
- 精選清單的排列順序就是新增的順序,這一輪不做拖曳排序。
- 既有的精選項目與新增的項目,「開好就自動下載」預設為否,要使用者自己打開。
- 對話頁轉送到模型服務的逾時沿用 001 Ollama 相容端點的設定(連線 10 秒;收到第一段之前與兩段之間 300 秒),逾時照 FR-008 標示中斷與原因。
- 精選清單編輯的錯誤代碼(`INVALID_MODEL_NAME`、`INVALID_CURATED_DESCRIPTION`、`CURATED_DUPLICATE`、`CURATED_NOT_FOUND`)沿用 001 `ui.openapi.yaml`,這一輪只補畫面與自動下載的欄位。
- 驗收以替身為主(遠端 Ollama、Hugging Face、`colab` 都用替身),不開 Colab、0 compute units;需要真的工作階段的實跑(例如真的從 Hugging Face 下載一個模型、真的對話),要不要做、預算多少,留到 testplan 停下來問使用者本人。
- 不在範圍內:需要登入的 Hugging Face 模型、對話紀錄保存、對話參數設定、精選清單拖曳排序、H100 以外的類型調整、001~003 完成報告列的其他待辦。
